# Проект: shortener

Сервис сокращения ссылок: создаёт короткий код для URL, перенаправляет по нему и считает переходы.
Стек: Go, REST, PostgreSQL, Docker. План разработки — в `docs/PLAN.md`.

## Стек
- Go (версия — из go.mod), стандартная библиотека в приоритете
- HTTP: `net/http`, роутинг через `http.ServeMux` с шаблонами путей (`GET /{code}`)
- БД: PostgreSQL + `pgx/v5` (`pgxpool`)
- Миграции: <goose | migrate/migrate — решить на шаге 5>
- Логи: `log/slog`
- Тесты: `testing` + table-driven тесты, `net/http/httptest`

## Команды
- Всё целиком: `docker compose up --build`
- Только БД: `docker compose up -d db`
- Миграции: `go run ./cmd/migrate`
- Запуск локально: `go run ./cmd/shortener`
- Тесты: `go test ./...` (интеграционные — только при заданном `TEST_DATABASE_URL`)
- Проверка: `go vet ./...`
- Перед коммитом: `go vet ./... && go test ./...`
- ОС: Windows (терминал Git Bash)

## Структура (лёгкий DDD в стиле Go)
- `cmd/shortener/main.go` — точка входа, только сборка зависимостей и запуск
- `cmd/migrate/main.go` — применение миграций
- `internal/link/` — домен ссылок
  - `link.go` — сущность, валидация URL, доменные ошибки; не знает про HTTP, SQL и JSON
  - `code.go` — генератор короткого кода
  - `service.go` — сценарии: Shorten / Resolve / Stats
  - `repository.go` — интерфейс хранилища, объявленный здесь, где он используется
- `internal/postgres/` — реализация репозитория
- `internal/httpapi/` — хендлеры: разбор запроса → вызов сервиса → ответ
- `migrations/` — SQL-миграции
- Никаких пакетов `utils`, `common`, `helpers`

## Разработка
- TDD: сначала падающий тест, потом минимальная реализация, потом рефакторинг
- Домен и сервис тестируются unit-тестами без БД и HTTP (фейковый репозиторий в `_test.go`)
- Хендлеры тестируются через `net/http/httptest`
- Репозиторий — интеграционными тестами, `t.Skip`, если не задан `TEST_DATABASE_URL`

## Правила
- Ошибки возвращаются, а не паникуют. Оборачивать с контекстом: `fmt.Errorf("find link %q: %w", code, err)`
- `context.Context` — первый параметр у функций с I/O
- Интерфейсы объявляются там, где используются, и только когда нужны (не «на будущее»)
- Конфигурация через переменные окружения (`PORT`, `DATABASE_URL`, `BASE_URL`), секреты только в `.env` (он в .gitignore)

## Принципы 12-factor (https://12factor.net/) — для HTTP-сервисов
- Конфиг только из переменных окружения, без хардкода адресов и паролей (III)
- БД, кэш, очереди — внешние ресурсы по URL из env; сменить базу = сменить переменную (IV)
- Процесс без состояния: ничего важного в памяти и на локальном диске между запросами (VI)
- Порт из env (`PORT`), сервис сам слушает порт (VII)
- Быстрый старт и graceful shutdown по SIGINT/SIGTERM через `signal.NotifyContext` (IX)
- Локально всё поднимается через Docker Compose, как можно ближе к «проду» (X)
- Логи через `log/slog` в stdout, никаких лог-файлов из приложения (XI)
- Миграции и разовые задачи — отдельной командой (`cmd/migrate`), а не при старте сервиса (XII)

## Принятые решения (не менять без моего согласия)
- Роутинг только на `net/http`, без chi/gin
- Только REST; gRPC — после MVP
- Сразу PostgreSQL, без промежуточного in-memory хранилища
- Код ссылки: 7 символов base62 из `crypto/rand`; уникальность гарантирует UNIQUE в БД,
  при коллизии сервис повторяет генерацию (до 3 раз)
- Счётчик кликов увеличивается атомарно одним UPDATE в БД
- Доменные ошибки (`ErrInvalidURL`, `ErrNotFound`, `ErrCodeTaken`) объявлены в `internal/link`;
  HTTP-коды назначает только `httpapi`
- Применённые миграции не редактировать, только новые
- Подробные решения с причинами — в docs/adr/ (по файлу на решение)

## MVP (текущая цель)
- `POST /links` — создать короткую ссылку (только абсолютные http/https URL, иначе 400)
- `GET /{code}` — редирект 302 и +1 к счётчику; нет кода — 404
- `GET /links/{code}` — статистика: url, code, clicks, created_at
- `docker compose up` поднимает API и PostgreSQL
- CI: GitHub Actions, `go vet` + `go test`
