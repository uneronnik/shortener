# План завершения shortener

Функциональный MVP реализован: сервис создаёт короткие ссылки, перенаправляет по ним
и возвращает статистику; данные хранятся в PostgreSQL. Реализованы ограничения
времени обработки запросов и безопасная диагностика внутренних ошибок.

Каждый этап изменений — отдельная рабочая ветка и PR с проверками.

## Выполнено

- [x] **1. Скелет.** `cmd/shortener/main.go`: `GET /healthz`, порт из `PORT`, `slog`, graceful shutdown
  (`signal.NotifyContext` + `http.Server.Shutdown`).
  *Тест:* `httptest` — `/healthz` отвечает 200.
- [x] **2. Домен.** `link.New(url)` с валидацией (пусто, `ftp://`, относительный путь, нет хоста, ок);
  генератор кода — 7 символов base62 из `crypto/rand`.
  *Тест:* табличный тест валидации; длина и алфавит кода.
- [x] **3. Сервис.** `Shorten`, `Resolve` (URL + инкремент счётчика), `Stats`; повтор до 3 раз при
  `ErrCodeTaken`; `ErrNotFound`.
  *Тест:* фейковый репозиторий в `_test.go`, фиксированный генератор для проверки повтора.
- [x] **4. HTTP-слой.** `POST /links`, `GET /{code}`, `GET /links/{code}`; JSON; ошибки → 400/404/500;
  `BASE_URL` из env.
  *Тест:* `httptest` на каждый эндпоинт и код ответа.
- [x] **5. PostgreSQL в Docker.** `docker-compose.yml` с `db`; миграция таблицы `links`
  (`code` UNIQUE, `url`, `clicks`, `created_at`); `cmd/migrate`.
  Выбрана библиотека goose в `cmd/migrate`; SQL встроен через `embed.FS` ([ADR](adr/0001-database-migrations.md)).
  *Проверка:* `docker compose up -d db && go run ./cmd/migrate` создаёт таблицу.
- [x] **6. Репозиторий на pgx.** `Save` (unique_violation 23505 → `ErrCodeTaken`), `FindByCode`,
  атомарный `UPDATE ... SET clicks = clicks + 1 RETURNING url`.
  *Тест:* интеграционные тесты при `TEST_DATABASE_URL`, иначе `t.Skip`.
- [x] **7. Минимальный CI.** GitHub Actions на pull request в `main` и push в `main`:
  версия Go из `go.mod`, сервис PostgreSQL 17, `go vet ./...` и `go test ./... -count=1`
  с заданным `TEST_DATABASE_URL`, чтобы интеграционные тесты не пропускались.
  *Проверка:* успешный запуск workflow в PR, включая тесты миграций и репозитория.
  После первого успешного запуска проверка сделана обязательной для слияния через правила ветки `main`.
  - [x] Workflow `CI` с job `Go checks`: Go из `go.mod`, PostgreSQL 17, vet и тесты с БД.
  - [x] Обязательная проверка `Go checks` от GitHub Actions в активном правиле `main`, без обходов;
    ветка PR должна быть актуальна относительно `main`.
- [x] **8. Сборка целиком.** Wiring в `main.go`, многостадийный `Dockerfile`, приложение в compose.
  *Проверка:* `docker compose up` + curl-примеры из README.
- [x] **9. Документация и полировка.** README с запуском полного приложения,
  настройкой окружения, диагностикой ошибок запуска и ручной проверкой API и сохранения данных.

## Критерии готовности MVP

- [x] README описывает запуск API, PostgreSQL и миграций через Docker Compose.
- [x] Создание ссылки возвращает `201`, переход — `302` и увеличивает счётчик,
  статистика возвращает исходный URL, код, число переходов и время создания.
- [x] Некорректный запрос возвращает `400`, отсутствующий код — `404`;
  обработка ошибок проверяется HTTP-тестами.
- [x] Ссылки и счётчики сохраняются после `docker compose down` без удаления volume
  и повторного запуска; сценарий ручной проверки описан в README.
- [x] `go vet ./...` и тесты с `TEST_DATABASE_URL` проходят;
  интеграционные тесты проверяют миграции и репозиторий PostgreSQL.
- [x] CI запускает проверки с PostgreSQL; `Go checks` обязателен для слияния в `main`.

## Надёжность и диагностика

- [x] **10. Таймауты и логирование внутренних ошибок.**
  Ограничить время чтения тела HTTP-запроса и обработки операций сервиса,
  включая ожидание соединения из пула и выполнение SQL. Передавать контекст
  с дедлайном до репозитория, сохранив отмену при отключении клиента.
  Согласовать таймаут записи HTTP-ответа с бюджетом обработки запроса.
  Значения таймаутов задавать через переменные окружения с разумными значениями
  по умолчанию; документировать их и проверять конфигурацию при запуске.
  Записывать внутренние ошибки через `slog` в stdout с операцией и причиной,
  сохраняя безопасный ответ клиенту без технических деталей.
  Исключить из логов пароли, строки подключения, тела запросов и исходные URL.

  Реализация: `HTTP_READ_TIMEOUT=5s`, `OPERATION_TIMEOUT=3s`,
  `HTTP_WRITE_TIMEOUT=10s`; проверка положительных длительностей и бюджета записи.
  Таймаут тела запроса возвращает `408`, дедлайн операции — `503`.
  Причины ошибок логируются безопасными категориями и SQLSTATE без исходного текста.
  Подробности и ограничения отмены — в [ADR](adr/0002-request-timeouts-and-error-logging.md).

- [x] Медленная отправка тела запроса ограничена по времени.
- [x] Истечение дедлайна и отмена клиентского запроса доходят до операций БД;

- [x] README и `.env.example` описывают новые настройки и поведение при таймауте.
- [x] Проходят `go vet ./...`, unit-тесты и интеграционные тесты с PostgreSQL;
  CI в PR успешен.
- [x] После изменения выполнен полный сценарий из README: создание, редирект,
  статистика, ошибки и сохранение данных после перезапуска Compose.
